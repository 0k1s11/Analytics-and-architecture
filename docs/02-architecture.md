# 02 — Architecture

## 1. Стек и границы

Документ содержит стек, обоснование выбора, C4 Context, C4 Container, backend-компоненты и границы ответственности.

### 4.2. Зафиксировать стек и границы системы

Frontend — HTML5 + CSS3 + JavaScript ES6+; Backend — Java 21 + Spring Boot 3.4; DB — PostgreSQL 16; ORM — Hibernate 6 + Spring Data JPA; API — REST/JSON; автотесты — JUnit 5 + Mockito; миграции — Flyway; файлы — ./uploads; запуск — localhost.

Обоснование выбора стека

Скорость разработки и декларативность — связка HTML/CSS/JS на фронтенде и Spring Boot со Spring Data JPA на бэкенде исключает написание шаблонного кода (boilerplate), позволяя быстро реализовать CRUD-операции и бизнес-логику MVP.

Стандартизация взаимодействия (REST/JSON) — использование классической REST-архитектуры и формата JSON обеспечивает простой, предсказуемый и слабосвязанный обмен данными между клиентской частью и сервером.

Надёжность и качество кода — строгая типизация Java 21 минимизирует ошибки во время компиляции, а связка JUnit 5 + Mockito позволяет изолированно тестировать бизнес-логику сервисов с помощью мокирования внешних зависимостей.

Зрелость и предсказуемость экосистемы — PostgreSQL 16, Hibernate 6 и Flyway гарантируют надежное хранение данных, строгий контроль схемы через версионируемые миграции и бесшовное управление сущностями.

Знакомство команды и простой локальный запуск — стек полностью соответствует компетенциям команды, а архитектура с хранением файлов в ./uploads позволяет запускать проект на localhost без необходимости сложной инфраструктуры и контейнеризации.

Границы модулей системы

auth — авторизация пользователей, проверка учётных данных и контроль доступа.

users — хранение и получение данных пользователей.

objects — создание, просмотр и управление объектами ремонта.

memberships — добавление пользователей в объекты и определение их ролей (CUSTOMER, EXECUTOR).

work-items — создание и управление карточками работ, назначение исполнителя и изменение статусов.

submissions/media — отправка результатов работы, загрузка и хранение фотографий.

comments — создание и просмотр комментариев к карточкам работ.

status-history — фиксация и хранение истории изменения статусов карточек.

### 4.3. Описать архитектуру

1. C4 Context

```flowchart LR

Customer[Заказчик]

Executor[Исполнитель]

System[Система «Ремонт под контролем»]

Customer -->|Работа с объектами, приемка работ, фиксация оплаты| System

Executor -->|Создание и выполнение работ, загрузка результатов| System

```

Легенда:

Заказчик — создаёт объекты, добавляет исполнителей, принимает работы и фиксирует оплату.

Исполнитель — создаёт карточки работ, начинает выполнение, загружает результаты и отправляет работы на проверку.

Система «Ремонт под контролем» — веб-система, управляющая объектами, работами, статусами, комментариями и результатами.

Направление вызовов: Пользователи → Система.

Протокол: HTTP/HTTPS через браузер.

Внешние зависимости: Внешние сервисы в MVP отсутствуют. PostgreSQL и локальное файловое хранилище являются внутренними компонентами системы.

2. C4 Container

```

flowchart LR

User[Пользователь]

Browser[Browser / Frontend<br/>HTML + CSS + JavaScript]

Backend[Backend API<br/>Java 21 + Spring Boot]

DB[(PostgreSQL 16)]

Files[Файловое хранилище<br/>./uploads]

User -->|HTTP| Browser

Browser -->|REST / JSON / HTTP| Backend

Backend -->|SQL / JDBC| DB

Backend -->|Чтение и запись файлов| Files

```

Легенда:

| Контейнер | Ответственность |
| --- | --- |
| Browser / Frontend | Отображение интерфейса, отправка запросов, отображение данных и ошибок |
| Backend API | Бизнес-логика, авторизация, проверка прав, управление статусами и данными |
| PostgreSQL | Постоянное хранение данных системы |
| ./uploads | Локальное хранение загруженных фотографий и других медиафайлов |

Направления вызовов:

Пользователь → Browser

Browser → Backend API

Backend API → PostgreSQL

Backend API → ./uploads

Протоколы:

Browser → Backend: REST / JSON / HTTP;

Backend → PostgreSQL: SQL через JDBC;

Backend → ./uploads: файловая система.

Хранение данных:

PostgreSQL отвечает за пользователей, объекты, участников, карточки работ, комментарии, подачи результатов, метаданные файлов и историю статусов.

./uploads отвечает только за физические файлы.

Backend отвечает за проверку доступа к данным и файлам.

3. Backend Component

```

flowchart TB

API[REST API]

API --> Auth[auth]

API --> Users[users]

API --> Objects[objects]

API --> Memberships[memberships]

API --> WorkItems[work-items]

API --> Submissions[submissions / media]

API --> Comments[comments]

API --> History[status-history]

Auth --> DB[(PostgreSQL)]

Users --> DB

Objects --> DB

Memberships --> DB

WorkItems --> DB

Submissions --> DB

Submissions --> Files[./uploads]

Comments --> DB

History --> DB

```

Ответственность модулей

| Модуль | Ответственность |
| --- | --- |
| auth | Авторизация, проверка учётных данных, контроль доступа |
| users | Работа с данными пользователей |
| objects | Создание и управление объектами ремонта |
| memberships | Добавление участников и определение ролей в объекте |
| work-items | Создание карточек работ, изменение условий и управление жизненным циклом |
| submissions / media | Подача результатов работы, загрузка и получение фотографий |
| comments | Создание и просмотр комментариев |
| status-history | Фиксация всех изменений статусов |

Границы ответственности

Frontend отвечает за отображение интерфейса и взаимодействие пользователя с системой. Он показывает данные, формы, кнопки и сообщения об ошибках, а также отправляет запросы на Backend API.

Backend API является основным компонентом, в котором реализована бизнес-логика системы. Он выполняет проверку авторизации и прав доступа пользователей, управляет статусами карточек работ, обрабатывает бизнес-правила, взаимодействует с базой данных и отвечает за загрузку и получение файлов.

PostgreSQL используется для постоянного хранения данных системы: пользователей, объектов, участников, карточек работ, комментариев, истории статусов и метаданных файлов.

Локальная директория ./uploads используется для хранения физических файлов, например фотографий результатов выполненных работ.

## 2. API-контракт

Для MVP используется OpenAPI 3.1 YAML. Основные правила:

- REST/JSON;
- Bearer Token;
- `multipart/form-data` для фотографий;
- успешные ответы `200`, `201`, `204`;
- единый формат ошибок;
- переходы статусов через единый endpoint.

Исполняемый контракт находится в `openapi/openapi.yaml`.
