# 06 — Traceability and Tests

Документ содержит матрицы BR/FR/NFR, трассировку UI → API → данные → тесты и план разработки вертикальными срезами.

### 4.12. Сделать трассировку и план разработки

Трассировка должна обеспечивать связь между обязательным бизнес-требованием и его реализацией в пользовательском интерфейсе, API, модели данных и тестах. Для каждого обязательного бизнес-требования должна существовать возможность определить, где оно реализовано и каким тестом проверяется. Требования, не имеющие реализации или проверки, в MVP оставаться не должны.

### 4.12.1. Матрица трассировки

В качестве основных бизнес-требований используются:

BR-01 — изоляция данных;

BR-02 — неизменность условий карточки после перехода в IN_PROGRESS;

BR-03 — визуальное подтверждение результата фотографиями;

BR-04 — обязательная причина возврата на доработку;

BR-05 — прозрачность финансовых агрегатов;

BR-06 — разделение ролей при сдаче, приёмке и оплате.

| BR ID | UI | API | Данные | Тест |
| --- | --- | --- | --- | --- |
| BR-01 | ObjectListPage, ObjectPage, WorkItemPage | GET /api/objects ,  GET /api/objects/{objectId} ,  GET /api/work-items/{id} , endpoints участников и файлов | User ,  RepairObject ,  ObjectMember ,  WorkItem ,  MediaAttachment | AT-API-01, AT-API-02, AT-UI-01 |
| BR-02 | WorkItemPage | PATCH /api/work-items/{id} ,  POST /api/work-items/{id}/transitions | WorkItem | AT-API-05, AT-UI-04 |
| BR-03 | WorkItemPage / блок подачи результата | POST /api/work-items/{id}/submissions ,  POST /api/work-items/{id}/transitions | WorkSubmission ,  MediaAttachment ,  WorkItemStatusHistory | AT-API-17, AT-UI-08 |
| BR-04 | WorkItemPage / форма возврата на доработку | POST /api/work-items/{id}/transitions | WorkItemStatusHistory ,  Comment | AT-API-18, AT-UI-09 |
| BR-05 | ObjectPage / финансовый блок | GET /api/objects/{objectId} | WorkItem.price ,  WorkItem.status | AT-API-20, AT-UI-10 |
| BR-06 | WorkItemPage | POST /api/work-items/{id}/transitions | WorkItem ,  WorkItemStatusHistory | AT-API-21, AT-UI-11 |

API-контракт уже предусматривает отдельные операции для объектов, карточек и переходов статусов, включая POST /api/work-items/{id}/transitions.

Для подачи результата предусмотрен отдельный endpoint POST /api/work-items/{id}/submissions, а для API используются Bearer Token, REST/JSON и multipart/form-data для загрузки фотографий.

### 4.12.3. Трассировка безопасности

Нефункциональные требования также должны быть проверяемыми.

| NFR | UI | API / Backend | Данные / инфраструктура | Тест |
| --- | --- | --- | --- | --- |
| NFR-SEC-01 Проверка доступа | состояния  forbidden | проверка пользователя, членства и роли на каждом защищённом запросе | User ,  ObjectMember | AT-SEC-01, AT-SEC-02 |
| NFR-SEC-02 Проверка файлов | форма загрузки | проверка MIME, Magic Bytes и размера | MediaAttachment ,  ./uploads | AT-SEC-03, AT-SEC-04 |
| NFR-SEC-03 Секреты | — | конфигурация приложения | .env , Git | AT-SEC-05 |
| NFR-PERF-01 Производительность | — | типовые API-операции | Backend + PostgreSQL | AT-PERF-01 |
| NFR-DEP-01 Развёртывание | — | localhost API | PostgreSQL,  ./uploads | AT-DEP-01 |

Backend отвечает за авторизацию, проверку прав, управление статусами и работу с данными, а PostgreSQL и ./uploads разделяют хранение структурированных данных и физических файлов.

### 4.12.4. План разработки вертикальными срезами

Разработка выполняется вертикальными срезами. Каждый срез должен заканчиваться работающим пользовательским сценарием, проходящим через UI → API → бизнес-логику → БД и имеющим соответствующие тесты.

Срез 1. Вход и профиль текущего пользователя

Результат: пользователь может войти в систему и определить свою текущую учётную запись.

Включает:

экран входа;

API авторизации;

проверку учётных данных;

идентификацию текущего пользователя;

отображение профиля/текущего пользователя;

обработку неверных учётных данных;

базовые тесты авторизации.

Самостоятельная регистрация и сброс пароля в MVP не входят.

Срез 2. Список объектов и доступ участников

Результат: авторизованный пользователь видит только доступные ему объекты.

Включает:

список объектов;

фильтры «Я заказчик» / «Я исполнитель»;

просмотр объекта;

просмотр участников;

проверку членства;

запрет доступа к чужому объекту;

тестирование 403/404 для недоступных ресурсов.

Это реализует прежде всего BR-01 и FR-04. API уже предусматривает получение списка объектов с фильтрацией по роли и получение конкретного объекта с проверкой доступа.

Срез 3. Создание объекта, добавление исполнителя, создание карточки

Результат: заказчик создаёт объект, добавляет исполнителя, после чего исполнитель создаёт карточку работы.

Включает:

создание объекта;

автоматическое назначение создателя CUSTOMER;

добавление исполнителя;

получение списка участников;

создание карточки работы исполнителем;

автоматическое назначение автора карточки исполнителем;

валидацию названия, стоимости и срока.

Этим срезом закрываются основные сценарии управления объектом и создания карточки. API-контракт предусматривает создание объекта, работу с участниками и создание WorkItem.

Срез 4. Полный happy path карточки до оплаты

Результат: можно полностью пройти основной сценарий от созданной карточки до статуса PAID.

Последовательность:

PLANNED → IN_PROGRESS → ON_REVIEW → AWAITING_PAYMENT → PAID

Включает:

запуск работы;

блокировку названия, описания, стоимости и срока;

загрузку 1–10 фотографий;

отправку результата на проверку;

приёмку заказчиком;

фиксацию оплаты заказчиком;

запись истории переходов;

пересчёт финансовых агрегатов.

Основной FSM и обязательность истории переходов уже зафиксированы в функциональных требованиях.

Срез 5. Возврат на доработку, история, негативные сценарии и полировка демо

Результат: система поддерживает альтернативную ветку процесса и готова к демонстрации.

Включает:

возврат ON_REVIEW → REWORK;

обязательную текстовую причину возврата;

возврат REWORK → IN_PROGRESS;

комментарии участников;

просмотр истории статусов;

проверку запрещённых переходов;

проверку попыток доступа пользователем без нужной роли;

проверку некорректных файлов;

проверку ошибок валидации;

обработку ожидаемых ошибок API;

финальную проверку основного demo-flow.

При этом под «чатом» в рамках MVP понимаются комментарии к карточке, а не realtime-чат через WebSockets: realtime-чат прямо указан в backlog.

### 4.12.5. Критерий завершения разработки

Разработка считается трассируемой и готовой к приёмке, если для каждого обязательного бизнес-требования можно однозначно ответить на четыре вопроса:

Где пользователь это делает? → Какой API это реализует? → Где это хранится? → Каким тестом это проверяется?
