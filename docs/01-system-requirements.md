# 01 — System Requirements

Документ содержит нефункциональные требования, безопасность и требования к localhost-развёртыванию.

✅ 4.10

### 4.10. Нефункциональные требования и безопасность

### 4.10.1. Требования к хранению паролей и секретов

Пароли пользователей не должны храниться в открытом виде.

В базе данных хранится только стойкий хеш пароля.

Для хеширования используется алгоритм, предназначенный для безопасного хранения паролей, например bcrypt, Argon2 или аналогичный.

Пароли, токены, ключи и другие секретные значения не должны храниться непосредственно в исходном коде и не должны коммититься в Git-репозиторий.

Секретные параметры приложения должны передаваться через переменные окружения или другой предусмотренный механизм конфигурации.

В репозитории допускается наличие .env.example, но он не должен содержать реальные секретные значения.

В модели данных поле User.password_hash предназначено именно для хранения хеша пароля, а не исходного пароля.

### 4.10.2. Серверная проверка прав доступа

Проверка прав доступа выполняется на backend при каждом API-запросе, затрагивающем объект, карточку работы, комментарий, подачу результата или файл.

Backend не должен полагаться только на ограничения интерфейса frontend.

Перед выполнением операции backend должен определить текущего пользователя и проверить его принадлежность к соответствующему объекту.

Дополнительно проверяется роль пользователя и наличие у этой роли права на выполняемую операцию.

Пользователь, не являющийся участником объекта, не должен получать доступ к связанным с ним данным или выполнять операции над ними.

При отсутствии необходимых прав запрос завершается отказом в доступе (403) либо 404 в случаях, когда необходимо не раскрывать факт существования ресурса.

Один пользователь может иметь разные роли в разных объектах, поэтому проверка роли выполняется в контексте конкретного объекта, а не только на уровне пользователя.

Данное требование является обязательным: серверная проверка доступа должна выполняться независимо от того, какие элементы интерфейса отображены пользователю.

### 4.10.3. Требования к загрузке фотографий

Для каждой подачи результата работы должны соблюдаться следующие ограничения:

количество фотографий — от 1 до 10 файлов;

допустимые форматы — JPG, PNG, WebP;

максимальный размер одного файла — 10 МБ;

проверка должна выполняться на стороне backend;

backend не должен доверять только расширению файла, переданному клиентом;

должен проверяться заявленный MIME-тип и фактический тип содержимого файла;

файлы, не соответствующие установленным ограничениям, не должны сохраняться.

Подача результата без необходимой фотографии не должна считаться корректной подачей работы.

### 4.10.4. Имена и пути файлов

Имя физического файла формируется сервером.

Клиентское имя файла может использоваться только как исходное метаданные, но не должно напрямую определять имя физического файла в хранилище.

Путь к файлу, переданный в request, не должен использоваться напрямую для формирования пути сохранения.

Пользователь не должен иметь возможности самостоятельно определить произвольный путь сохранения файла.

Загруженные файлы должны храниться отдельно от исходного кода и Git-репозитория.

Метаданные файла сохраняются в базе данных.

В архитектуре предусмотрено хранение физических файлов в директории ./uploads, а метаданных — в сущности MEDIA_ATTACHMENT.

### 4.10.5. Валидация входных данных

Backend обязан выполнять базовую валидацию всех входных данных до выполнения соответствующей операции.

Для строковых полей должны быть установлены ограничения длины. В частности:

название объекта — от 1 до 200 символов;

адрес объекта — до 500 символов;

название карточки работы — от 1 до 200 символов;

текстовые поля не должны принимать значения, нарушающие установленные ограничения.

Для стоимости:

значение не может быть отрицательным;

стоимость хранится с точностью до двух знаков после запятой;

денежные значения не используются в типах FLOAT или DOUBLE.

Для дат:

используется корректный формат даты;

плановая дата окончания объекта не может быть раньше плановой даты начала;

срок карточки должен передаваться как корректная дата.

Установленные ограничения должны проверяться backend независимо от валидации формы на frontend.

### 4.10.6. CORS

Backend должен разрешать кросс-доменные запросы только от адреса frontend, используемого проектом.

Произвольные внешние origins не должны разрешаться.

Настройка CORS не должна предоставлять общий доступ ко всем источникам.

### 4.10.7. Производительность и стабильность demo-flow

Для демонстрационного сценария устанавливаются следующие целевые показатели:

типовая API-операция должна выполняться не более чем за 1 секунду;

время загрузки бинарного файла в данный показатель не включается;

основной demo-flow не должен приводить к HTTP-ошибкам класса 5xx;

ожидаемые ошибки валидации, отсутствия прав или нарушения бизнес-правил должны обрабатываться как предусмотренные ошибки API, а не приводить к необработанному исключению и ответу 500.

Основной подход API предусматривает единый формат ошибок и использование стандартных HTTP-кодов для успешных и ошибочных операций.

### 4.10.8. Границы требований безопасности

В рамках MVP не требуется реализация production-ready уровня безопасности и масштабирования. При этом серверная проверка прав доступа и базовая валидация входных данных являются обязательными требованиями проекта.

Таким образом, для приёмки 4.10 необходимо подтвердить:

пароль в БД хранится только в виде хеша;

секреты отсутствуют в репозитории;

backend проверяет членство и роль при обращении к защищённым объектам и карточкам;

фотографии ограничены количеством, форматом и размером;

проверяется фактический тип загружаемого файла;

имя и путь физического файла определяются сервером;

входные строки, стоимость и даты проходят серверную валидацию;

CORS разрешает только frontend;

типовая API-операция укладывается в целевой показатель до 1 секунды без учёта загрузки файла;

основной демонстрационный сценарий не содержит необработанных ошибок 5xx.

### 4.11. Описать localhost-развёртывание

Для локального запуска системы необходимо обеспечить воспроизводимое развёртывание, позволяющее запустить backend, базу данных и frontend без ручной настройки отдельных компонентов.

### 4.11.1. Запуск системы

Локальное развёртывание должно выполняться:

одной командой или

не более чем тремя последовательными командами.

Порядок запуска должен быть однозначным и не требовать от пользователя ручного создания базы данных, таблиц или демонстрационных данных.

### 4.11.2. Конфигурация окружения

В проекте должен присутствовать файл .env.example, содержащий перечень необходимых переменных окружения без реальных секретных значений.

.env.example должен позволять определить необходимые параметры локального запуска, включая:

параметры подключения к БД;

порты backend и frontend;

настройки хранения загружаемых файлов;

параметры, необходимые для запуска приложения.

Реальные пароли, токены, ключи и другие секретные значения в .env.example и Git-репозитории отсутствуют.

### 4.11.3. База данных и миграции

При развёртывании должна автоматически или по предусмотренной команде выполняться миграция базы данных.

Миграции должны создавать структуру БД, необходимую для работы системы, включая сущности пользователей, объектов ремонта, участников объектов, карточек работ, комментариев, подач результатов, файлов и истории статусов.

Ручное создание таблиц непосредственно перед запуском системы не требуется.

### 4.11.4. Демонстрационные данные

Развёртывание должно предусматривать выполнение seed-скрипта с подготовленными демонстрационными данными.

В seed должны присутствовать как минимум:

подготовленная учётная запись заказчика;

подготовленная учётная запись исполнителя;

необходимые связи между пользователями и демонстрационным объектом;

данные, позволяющие пройти основной демонстрационный сценарий без предварительного ручного наполнения БД.

Исполнитель должен быть добавлен к объекту как его участник, после чего он получает доступ к объекту и может выполнять предусмотренные для его роли действия.

### 4.11.5. Порты и локальные URL

Документация по развёртыванию должна явно указывать используемые локальные порты:

backend API — порт, на котором запускается сервер;

frontend — порт, на котором доступен пользовательский интерфейс;

БД — порт используемой СУБД, если БД запускается отдельно.

Для backend в текущем API-контракте предусмотрен локальный сервер http://localhost:8080.

После запуска должны быть доступны:

frontend — через локальный адрес frontend;

API — через локальный адрес backend;

Swagger UI — через предусмотренный адрес документации API.

Конкретные URL Swagger UI и frontend должны быть указаны в инструкции запуска проекта и соответствовать фактической конфигурации приложения.

### 4.11.6. Health-check

Backend должен предоставлять health-check для проверки того, что приложение запущено и способно обслуживать запросы.

Health-check используется для проверки успешности локального развёртывания перед началом демонстрационного сценария.

Минимально необходимо подтвердить:

backend запущен;

приложение доступно по локальному порту;

необходимые зависимости приложения доступны;

после успешного health-check можно переходить к работе с системой.

### 4.11.7. Хранение загружаемых файлов

Для локального развёртывания должна быть определена отдельная папка для загружаемых файлов.

Файлы не должны сохраняться внутри исходного кода приложения таким образом, чтобы пользовательские загрузки попадали под версионирование Git.

В текущей архитектуре для локального хранения предусмотрена директория ./uploads, а сведения о файлах хранятся в MEDIA_ATTACHMENT.

### 4.11.8. Очистка демонстрационных данных

Должен быть определён порядок очистки локальных demo-данных перед повторным запуском демонстрации.

Очистка должна учитывать как минимум:

данные демонстрационной БД;

загруженные в рамках демонстрации файлы;

повторное выполнение миграций при необходимости;

повторное выполнение seed для восстановления исходного состояния демо.

После очистки и повторного seed система должна возвращаться в предсказуемое начальное состояние, позволяющее повторно пройти основной demo-flow.

### 4.11.9. Требования к Windows

Для Windows должны быть подготовлены команды запуска, миграции, seed и очистки, совместимые с используемой в проекте средой.

Команды и пути должны быть проверены минимум на одной Windows-машине, отличной от машины разработчика.

По результатам проверки необходимо убедиться, что:

проект запускается с чистого окружения;

указанные команды выполняются без ручного исправления путей;

необходимые каталоги создаются корректно;

миграции выполняются;

seed создаёт требуемые демонстрационные данные;

backend и frontend доступны по указанным адресам;

health-check проходит успешно;

Swagger UI открывается;

основной demo-flow может быть выполнен.

### 4.11.10. Критерии приёмки localhost-развёртывания

Развёртывание считается соответствующим требованиям 4.11, если:

система запускается одной командой либо максимум тремя последовательными командами;

присутствует .env.example без секретов;

БД разворачивается посредством миграций;

seed создаёт готовые учётные записи заказчика и исполнителя;

указаны порты backend, frontend и БД;

указан URL Swagger UI;

предусмотрен и проверен health-check;

указана папка хранения загружаемых файлов;

описан порядок очистки demo-данных;

команды и пути для Windows проверены на машине, отличной от машины разработчика.
